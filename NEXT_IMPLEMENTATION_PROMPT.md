## Implement next: apply monitoring settings without restarting the GUI

Start with `general.history_samples` and `general.poll_interval_ms` on successful **Import user settings → Apply settings**. `tests/gui_settings.py` currently verifies that the history limit reaches disk. Add a check that it takes effect in the same running process. Do this before taking on another launcher or hardware feature.

1. In `gui/src/charts.rs`, let the existing shared `History` adopt the new capacity in place. On shrink, immediately drop the oldest entries in every series; on growth, keep existing entries and allow future samples up to the new limit. Preserve gaps, original acquisition timestamps and source labels. Chart views, newly opened or explicitly refreshed history text, and new CSV exports should reflect the new buffer. An open history text snapshot should stay stable until explicitly refreshed, as it does during normal polling. A source identity change must still clear history.
2. Trace the actual poll interval and freshness consumers in `gui/src/main.rs`, `gui/src/pages.rs`, `gui/src/charts.rs`, `gui/src/overlay.rs`, and `gui/src/alerts.rs`. The worker captures its interval at startup; page freshness is separately cached in a `OnceLock`. Changing only the cache or history limit will not update the worker. Apply the validated user values from a successful save to the existing poller and the GUI freshness consumers. Preserve the current freshness bounds, stale-control gating and NVIDIA query limits. Avoid reading config from chart rendering, sensor lookups or on every poll. Keep the worker off the GTK main thread and avoid starting duplicate workers.
3. Connect the update to successful persistence in the User import path in `gui/src/pages.rs`; keep the current values after cancellation, invalid input or a failed write. Keep User and Service settings isolated. Leave unrelated preferences on their existing apply/restart behavior and state accurately in the import feedback which changes take effect now. Direct TOML edits and imports from a separate CLI process do not need live file watching for this change.

**Pass criteria:** A Rust regression demonstrates shrinking and growing a populated history, with two series, gaps and original sample identity intact. Exercise the existing acquisition freshness rule at an interval where the threshold actually changes (for example, 500 ms to 3,000 ms changes the derived cutoff from 7 to 9 seconds). Extend the private native settings workflow to collect more readings than the proposed new cap, import that lower cap and a changed poll interval, and observe the retained readings in refreshed history or CSV and the changed cadence on fresh fixture acquisitions, all in the same GUI process. Use bounded waits or a controllable fixture, not exact wall-clock sleeps. Verify canceled and rejected imports leave the active settings intact. Re-run the source-switch workflow to confirm different sources still reset history and stale controls still disable. If notification freshness changes, re-run the notification workflow too.
